# @getpaseo/watch — Paseo for Wear OS

Native Wear OS app: Kotlin + Compose for Wear. Triage and unblock agents from your
wrist, by voice or by typing.

**Status:** UI and the Wearable Data Layer bridge are both built. The watch renders
real wire JSON delivered through `DataClient`, and sends prompts, permission
responses, stops, and new-agent requests back over `MessageClient`.

What is verified, and what is not, is spelled out in [Verification](#verification) —
in particular the physical phone-to-watch hop has **not** been exercised, because
that needs a paired device.

The approved visual design and the information-architecture rules live in
[design/README.md](design/README.md) alongside a browser mock
(`design/watch-mock.html`). Read that before changing screen layout.

## Why this is a separate Gradle project

`packages/app/android` is generated by `expo prebuild` and is gitignored, so a
`:wear` module added there would be wiped on the next prebuild. This is a
standalone Gradle project instead; it shares no build with the Expo app.

It is also **not** an npm workspace package — nothing here is consumed by
JavaScript, and adding it to the workspace would put a Gradle project inside
`npm install`'s blast radius for no benefit.

## Architecture

Phone-tethered. The watch never speaks the Paseo WebSocket protocol:

```
Wear app  ──Wearable Data Layer──▶  Phone app  ──WebSocket──▶  Daemon
   │                                    │
   │  DataClient   /paseo/snapshot  ◀────┤  phone publishes state
   └─ MessageClient /paseo/command  ────▶│  watch sends intents
      MessageClient /paseo/refresh  ────▶│  watch asks for a republish
```

The phone app owns the daemon connection, pairing, and relay E2EE. The watch
receives a flattened snapshot and sends back intents.

**Why two different primitives.** Snapshots go over `DataClient` because it persists,
syncs on its own schedule, and redelivers the latest item when the watch comes back
into range — so the list is never blank just because the link blipped. Commands go
over `MessageClient` because it fails fast: silently queueing "approve this
permission" for delivery an hour later would be worse than an honest failure.

### The pieces

| Where                                    | What                                                          |
| ---------------------------------------- | ------------------------------------------------------------- |
| `data/WearBridge.kt`                     | Wire contract + codec (watch side)                            |
| `data/DataLayerRepository.kt`            | `WatchRepository` over DataClient/MessageClient               |
| `packages/expo-wear-bridge`              | Expo native module exposing the Data Layer to JS              |
| `packages/app/src/wear/wear-protocol.ts` | Wire contract (phone side) — mirror of `WearBridge.kt`        |
| `packages/app/src/wear/wear-snapshot.ts` | Flattens session-store state into the snapshot                |
| `packages/app/src/wear/wear-bridge.ts`   | Publishes snapshots, executes commands against `DaemonClient` |

The Expo module is a separate workspace package rather than code inside
`packages/app/android`, because that directory is regenerated by `expo prebuild`.

### Known limitation: commands while the phone app is dead

Play Services starts `PaseoWearListenerService` even when the phone app's process is
gone, so the message arrives — but there is no JS runtime to execute it against.
Rather than spin up React Native headlessly (slow and unreliable), the command is
persisted to a small on-disk queue and drained the next time the app starts.

So: **a command sent while the phone app is killed takes effect when the app is next
opened, not immediately.** The watch reports send failures rather than pretending
success, and `WearBridge.start()` drains the queue before its first publish so a
queued approval isn't immediately overwritten by a snapshot that still shows it
pending.

### What the watch deliberately does not get

`summary` on each agent is the daemon's **agent title**, not the transcript tail.
Populating the real last assistant message would mean subscribing to every agent's
timeline from a background bridge; the title is both cheaper and the right altitude
for a wrist.

## Voice and typing

Both come from Wear's system input sheet via `RecognizerIntent`
(`ui/ReplyScreen.kt`), with `EXTRA_PREFER_OFFLINE` so it keeps working without a
network. Google's on-device recognizer returns a finished string; no audio ever
touches our code, and there is no `RECORD_AUDIO` permission.

Paseo's own daemon-side dictation pipeline (`dictation_stream_*` in
`packages/protocol/src/messages.ts`) is deliberately **not** used. With a
phone-tethered transport, streaming PCM off the watch is a bad trade against a free
on-device recognizer. If the watch ever goes standalone, revisit this.

## Layout of the source

| Path                      | What's in it                                                         |
| ------------------------- | -------------------------------------------------------------------- |
| `model/Models.kt`         | Display models + the workspace→destination navigation rule           |
| `data/WatchRepository.kt` | Repository interface + the mock implementation                       |
| `theme/Theme.kt`          | Paseo dark tokens; project-icon palette and hash ported from the app |
| `ui/`                     | One file per screen, plus `Components.kt` and `Glyphs.kt`            |
| `PaseoWatchApp.kt`        | Nav host; the only place navigation decisions are made               |

Two invariants worth not breaking:

- **The "skip the picker" rule lives in exactly one place** —
  `Workspace.destination()` in `model/Models.kt`, applied once in
  `PaseoWatchApp.kt`. One agent goes straight to the agent; zero agents go straight
  to a voice prompt; the picker is only for genuinely ambiguous workspaces. Don't
  re-derive this at call sites.
- **The project-icon color hash is a port, not an invention** — it mirrors
  `packages/app/src/utils/project-icon-color.ts` so a project is the same color on
  wrist and phone. Change both or neither.

## Build

Requires JDK 17+ and an Android SDK with API 36 and build-tools 35+.

```bash
cd packages/watch
echo "sdk.dir=/path/to/android-sdk" > local.properties
gradle :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

`gradle` here is any Gradle 8.13+; the repo pins AGP 8.13.2 and Kotlin 2.3.21 in
`gradle/libs.versions.toml`.

### Running on a Wear emulator

A Wear OS AVD with a round 450×450 display:

```bash
avdmanager create avd -n paseo-wear -k "system-images;android-35;android-wear;x86_64"
emulator @paseo-wear -no-window -gpu swiftshader_indirect
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n sh.paseo.watch/.MainActivity
adb exec-out screencap -p > /tmp/watch.png
```

If `avdmanager` refuses the system-image path (older cmdline-tools can't parse
newer `package.xml`), write `~/.android/avd/<name>.ini` and
`<name>.avd/config.ini` by hand with `tag.id=android-wear`,
`hw.lcd.width/height=450`, and `hw.lcd.circular=yes`.

## Wear Compose Material 2, not Material 3

`gradle/libs.versions.toml` pins `androidx.wear.compose:compose-material` (M2). The
chip and round-button vocabulary in the approved design maps onto it 1:1, and
`TimeText`/`Vignette` give the watch chrome for free. Wear Material 3 renames most
of that surface; migrating is a deliberate later step, not a v1 risk.

## Verification

Verified:

- **Watch unit tests** (`gradle :app:testDebugUnitTest`) — 10 tests pinning the wire
  format, version rejection, unknown-state degradation, and the navigation rule.
- **Phone unit tests** (`vitest run src/wear/wear-bridge.test.ts`) — 23 tests covering
  snapshot building, command parsing, permission routing, the killed-app drain, and
  failure handling.
- **On-device Data Layer read path** (`gradle :app:connectedDebugAndroidTest`) — puts a
  real DataItem and asserts the repository picks it up, decodes it, and maps it.
- **On-device rendering of real wire JSON** — see
  `design/screenshots/bridge-*.png`. Those are the app driven by a DataItem
  delivered through `DataClient`, not mock data.

**Not verified:** the physical phone-to-watch hop, and the phone side's native module
(`publishSnapshot`, the listener service, the disk queue) running on a real device.
Both need a paired phone + watch, which needs a Google account on the emulator pair.
Everything on either side of that hop is tested; the hop itself is not.

To exercise the watch against real JSON without a paired phone:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb shell am instrument -w -e class sh.paseo.watch.data.SeedSnapshotTool \
  sh.paseo.watch.test/androidx.test.runner.AndroidJUnitRunner
adb shell am start -n sh.paseo.watch/.MainActivity
```

Use `am instrument` rather than `gradle connectedDebugAndroidTest`, which uninstalls
the app afterwards and takes the seeded DataItem with it.

`MainActivity.USE_MOCK_DATA` also flips the whole app back to `MockWatchRepository`.

## Roadmap

1. **Pair a real phone and watch** and confirm the hop, including a command sent while
   the phone app is killed.
2. **Notifications.** Permission requests as bridged notifications with `RemoteInput`
   reply. The phone app currently has no notification actions at all — no
   `setNotificationCategoryAsync` anywhere in `packages/app/src` — so this is
   greenfield, and it's independently useful even without the watch app.
3. **Tile.** Running count + needs-approval, per the design mock. Needs
   `androidx.wear.tiles` + protolayout.
4. **Distribution.** Play Console form-factor listing, and a decision on whether
   F-Droid ships this at all — `play-services-wearable` is a proprietary dependency,
   so an F-Droid build of the phone app must exclude `packages/expo-wear-bridge`.
